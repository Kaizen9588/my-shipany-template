## 一、阻断项

### P0-1 退款/拒付对「已消费积分」没有任何回收路径，§4.3 的方案 A 和 B 都不闭环

**位置**：`docs/05-payment-credits-flow.md` §4.2 场景 2 / §4.3 / §5.1 P0-退款-1
**交叉**：`docs/03-database-schema.md` 的 `credit_lots`、`credit_refunds`、`refunds` 表定义

**失败时序**：

1. 付款成功，`handle_order_payment` 发放 300 积分
2. 用户当天把 300 积分全部消费在 AI 调用上（上游算力成本已实际发生）
3. 用户向渠道申诉退款，`refund.created` webhook 到达
4. `process_order_refund` 扣回 `LEAST(订单积分 300, 当前余额 0)` = **0**
5. 订单进终态 `refunded`，钱全退，余额 0

文档给的两条整改路径都盖不住这条时序：

- **方案 A**（只允许严格全额退款）对已消费部分**零覆盖**，反而把「可能白嫖」变成「必然白嫖」
- **方案 B**（按比例或按消费批次回收）在批次 `remaining_credits` 已归零时**无回收对象**——`credit_lots.remaining_credits`、`credit_refunds.refunded_credits`、`refunds.credits_refunded` 全部是非负语义，全库**没有任何负批次/欠款的表达**（引入批次模型恰恰是为了废弃永久负数流水）

真正缺的不是账本形态，是**退款准入校验 + 债务化**：webhook 一到就无条件终态化，没有需要人工决策的中间态。

**修法**：

1. `orders` 增加 `refund_requested` / `refund_blocked` 状态；webhook 到达只**登记退款事实**并触发资产回收流程，不再直接写 `refunded`，终态由回收流程闭合
2. 退款准入校验：`refundable_amount = order.amount × (该订单批次 remaining_credits / 订单发放积分)`。默认只放行未消费比例；超出部分走显式审批（记 operator + reason）
3. 越权全额退款时把差额债务化：`credit_lots` 增加 `debt` 类型，或独立 `credit_debts(user_uuid, order_no, credits, status)`；账号进 `restricted`，清偿前禁止消费与再次下单
4. AI 网关侧对「新账号 + 首充后 24h 内高速耗尽积分」加节流，把白嫖窗口拉长到超过渠道退款风控识别时间
5. 业务层兜底不要省：退款条款写明「已消费积分不予退还」，争议举证材料（调用日志 + 消费流水）在 dispute 时可导出

**必须改验收标准**：P0-退款-1 现在写的是「v1 只允许全额退款，或完成 refunds 表 + 比例/批次扣回」——照这个标准可判定已关闭而口子原样敞着。应改为「**退款准入校验 + 已消费额度债务化 + refund_blocked 人工态**」三项齐备。

> **客观边界**：损失上界是 COGS 不是收入（每轮仍需真实付款并过 MoR 反欺诈），别按「无限刷钱」估算。但 Creem 无退款 API、MoR 对消费者申诉极宽松，这条路随时会被触发。

### P0-2【新发现】`decrease_credits` 的「行锁串行化」论证不成立

**位置**：`docs/03-database-schema.md:249`「行锁锁定该用户全部积分记录（串行化并发扣减）」、`docs/03:637`
**错误自认散布在**：`boundary-spec.md:47`、`docs/README.md:61`、`docs/05:207`、`docs/13:43`、`docs/15:46`

扣减的写入方式是 **INSERT 一条负数流水**，不是 UPDATE 已有行。`SELECT ... FOR UPDATE` 只锁查询快照里**已存在**的行，对并发插入的新行没有谓词锁/间隙锁。所以「锁 + SUM 校验 + INSERT 负数」这套组合在 append-only 账本上并不等价于串行化。

讽刺的是 `docs/03:11` 和 `:630` 开篇就写着「应用层禁止 check-then-write（多实例并发下必然出双花/透支窗口）」，而存储过程内部结构正是 **DB 层的 check-then-write**。

**诚实说明**：是否真的能双花，取决于 SUM 校验是与 `FOR UPDATE` 同一条语句，还是解锁后另起一条语句（READ COMMITTED 下后者会重取快照从而看到对方的提交）。文档没有规定这一点，也没有任何隔离级别分析——全仓 grep `advisory` / `SERIALIZABLE` / `幻读` **零命中**。

所以准确的定性是：**这是一个被标成 ✅ 的、未经论证的并发安全声明，而它保护的是资金**。这个级别的东西不能靠「实现细节可能刚好对」。

**后果如果成立**：直接映射上游 AI 推理成本资损，且**运营侧完全不可见**——`getUserCredits` 的 `Math.max(0)` 把负余额显示成 0（`docs/05 §2.5`）。`docs/13` 的限流是内存级、多实例不共享、重启清零，兜不住。

**修法**（推荐 2）：

1. **快修**：`decrease_credits` 开头 `PERFORM pg_advisory_xact_lock(hashtext(p_user_uuid))`（pooler 事务模式下必须用**事务级**，session 级不可用）
2. **正解**：迁到 `credit_lots` 后改为 `UPDATE credit_lots SET remaining_credits = remaining_credits - x WHERE id = ? AND remaining_credits >= x`，靠 UPDATE 自身行锁 + 返回行数保证原子。**这是批次模型相对净额模型的核心收益之一，应当补进 `docs/05 §2.4` 的论证里**——现在只提了过期/退款/审计三个维度，完全没提并发
3. **兜底**：`credit_balances(user_uuid PK, balance)` 物化余额行 + `CHECK(balance >= 0)`，让 DB 约束兜底

**并发回归测试必须进验收标准**：N 并发扣减，断言余额恒 ≥ 0 且成功次数 = `floor(余额 / 单价)`。

### P0-3【新发现】自动迁移向生产库种入全网公开的 super_admin 弱口令

**位置**：`docs/boundary-spec.md §二`（标 ✅ 已落地）、`docs/03` 迁移清单 0012、`README.md:14` 与 `:178-190`（逐字公开 `admin@shipany.local` / `123456` / `super_admin`）

「首次强制改密」只是**登录之后**的跳转。账号本身在迁移执行完那一刻就已可用公开凭据登录——**谁先登谁改密**。

而迁移是 `instrumentation.ts` 服务启动时自动执行（`docs/07 §5.2.1` 第 4 步、`README:164` 都确认），生产实例第一次冷启动就把该账号写进生产库。全仓 grep `NODE_ENV` / 「仅开发」/ `bootstrap`，没有任何一处把 0012 限定为非生产。

**后果**：部署者通常先配域名/支付，几小时后才首次登录。窗口内拿到 super_admin 即可：退款/调账（`system_add` 无上限）、改 `payment_products` 定价、读后台明文回显的通知 webhook secret（N-1 已自认）、封禁真实管理员。利用有时序与发现门槛，但这是教科书级默认口令缺陷（CWE-1392）。

**修法**：

1. 0012 改为条件建号：仅当 `ADMIN_BOOTSTRAP_EMAIL` 显式设置时创建
2. 密码取 `ADMIN_BOOTSTRAP_PASSWORD` 或迁移内 `gen_random_uuid()` 随机生成，只写一次启动日志
3. 建号时 `status='pending_activation'`，必须邮箱验证激活后才允许密码登录
4. `NODE_ENV=production` 默认不建任何管理员，改由 CLI 人工执行
5. README 删除逐字凭据表，改为「启动日志中会打印一次性初始密码」
6. `boundary-spec §二` 该行 ✅ → ❌ 并进 §九 No-Go 清单

> 同表相邻行（webhook secret）一有洞就标 ⚠️ 并进 No-Go，说明 ✅ 在这份文档的语义里就是「无缺口」。这是明确的错误自认。

### P0-4 匿名 demo「失败退还次数」+「输入无大小限制」= 单 IP 绕过每日 3 次

**位置**：`docs/14-anonymous-trial.md §2.5`（`GREATEST(count-1, 0)` 退还）、`§五` 防刷边界表
**交叉**：`docs/13-ai-gateway.md §八`（「输入无大小限制 | P1 | ❌ prompt/messages 无 schema、无字节限制、无消息条数上限」）

`/api/v1/ai/demo` 是无认证入口，唯一成本闸门是「每 IP 每天 3 次」，`DEMO_MAX_TOKENS` 只限**输出**，没有任何秒级/分钟级限流。

RPC 先自增、失败路径再 `GREATEST(count-1, 0)` 减回——**闸门只对成功的调用计数，而攻击者可以让 100% 的调用失败**：

```
单 IP 发超大 prompt（无 schema、无字节上限）
  → provider 因超上下文返回 400
  → 服务端判为「模型报错」
  → 退还次数，count 回 0
  → 循环
```

`anonymous_usage` 表因为一直被减回去，**监控上看不到任何异常**（`docs/16` 全文无 AI 成本/错误率告警条目）。`§五`「防刷边界（诚实声明）」只列了「换 IP 可绕过」，**没意识到不换 IP 也能无限调用**。

**修法**：

1. 匿名端点在**扣次数之前**做输入硬校验：字节上限（如 8KB）、消息条数上限、字段白名单；超限直接 413 且**照常消耗次数**（否则校验本身成了免费重试通道）
2. `§2.5` 改为：退还只在「已确认上游未产生费用」的错误类型（本地 5xx、provider 连接失败/超时）时执行；**provider 返回的 4xx、内容策略错误一律计次**。措辞与 `docs/13:196` 的 `ai_refund`「仅服务端异常时」语义对齐
3. 加一层与业务成败无关的 IP 秒级/分钟级限流（fail-closed，对应 `boundary-spec:71/89` 已挂账的 N-5），并对「同一 anonymous_key 当日失败次数」单独计数封顶
4. `§五` 防刷边界表补上这条——当前那张表是不完整的「诚实声明」

> **客观边界**：增量危害是把攻击成本从「需代理池」降到「一个 IP」，而不是从有界变无界。但既然措辞含糊会被实现者按字面落地，就必须在文档里钉死。

### P1-5 幂等键作用域

全局唯一 + 客户端可控 = 键空间是公共资源。批量抢注 `"1"`、`"test"`、常见客户端库默认键，受害者用同名键请求时要么被永久拒服（无 TTL 字段、无自助恢复），要么在「冲突返回已有记录」的实现下读到别人的结果。

严格说这是**欠规定**而非已成事实的漏洞（`ai_requests` 位于 `03` 的「规划中 / v1 收费前必须完成」，尚未建表；`02` 已写明按用户作用域，实现者照做即可避免跨租户）。

**修法**：`UNIQUE (user_uuid, request_id)`（匿名端点用 `anonymous_key` 作租户维度）+ `13 §六` 补齐键的必填性/字符集/长度 + 存请求体指纹 `hash(model+prompt+max_tokens)`、同键不同体返 422 + 用 `created_at` 落地 `02` 的 24h 口径与清理任务。

> 顺带纠正一处：审查中曾提出「持 `sk-` 的第三方可跨租户」不成立，`02:81` 明确 API Key 与 Session 映射同一 `user_uuid`。

### P1-6 两条互斥建库路径

`docs/07` 作为**唯一的部署入口文档**在 `§2.1` 前置条件、`§5.2.1` 云端第 2 步、`§5.2.2` 本地三处都要求先手工执行 `data/install.sql`（6 表），还写了「顺序硬约束：必须先跑 install.sql 再让迁移跑起来——迁移 0004 的外键依赖基础表」。

**这条硬约束的理由本身已过期**：基础表由 `0000_install_base.sql` 创建（7 表），0004 的依赖天然由迁移序列满足。而 `docs/03 §概述` 明写 `install.sql`「与迁移基线存在出入，勿再参考」。README 又给了第三条路径（从 0000 起逐条粘贴，与 03 一致）。

三处并存，**没有一处被标为唯一真相源**，而 `07` 是唯一的离群者且是最权威入口。按文档字面推演最可能是首次启动 `relation already exists` 崩溃（响亮失败，接量前会暴露），所以定 P1 不定 P0；但这个后果本身就该在 No-Go 清单里，`07 §5.6` 已知问题现在只列了 EMFILE / npm EPERM / 端口占用。

**修法**：`07` 删掉三处 `install.sql` 引用与「顺序硬约束」整段，统一为「空库 → 只跑 `data/migrations/*`，0000 即基线」；`data/install.sql` 移入 `legacy/` 并在文件头标废弃；`lib/migrate.ts` 加基线断言（`schema_migrations` 为空但 `users` 已存在 → fail-fast）；三处建库说明只保留一处，其余改链接。

### P1-7 自动迁移的并发与发布顺序

「`schema_migrations` 版本表保证幂等」只解决同一进程重复启动不重跑，**不解决多进程同秒启动**。而 `07 §1` 首选 Vercel、`§2.2` push 即自动部署、`08` 推荐 pooler 事务模式——「多实例 + 运行时自动迁移 + pooler」三者叠加正是文档自己推荐的默认形态。

全库 grep `advisory lock` / `同事务` / `down 脚本` / `回滚` / `expand-contract` / `CONCURRENTLY` **零命中**；迁移失败后是否继续启动也没定义。最确定会炸的是 0002/0003 的 `CREATE OR REPLACE FUNCTION` 并发执行撞 `tuple concurrently updated`。

**修法**：迁移器入口 `pg_advisory_xact_lock(固定key)`（**事务级**，pooler 下可用）；每条迁移与 `INSERT INTO schema_migrations` 同事务；失败 fail-fast 阻止服务接流量；把迁移从 `instrumentation.ts` 剥离为流水线前置步骤，运行时只校验「schema 版本 ≥ 代码要求版本」；建索引一律 `CONCURRENTLY` 且单独成条；补 expand-contract 规则（删列/改名拆两次发布）。另外 `03:586` 把「无数据库迁移工具」标成 ✅ 已落地，需改成「最小机制已落地，并发/回滚/发布顺序未覆盖」。

### P1-8 定价真相源两份文档互相矛盾

定价真相源在文档间直接打架：

| 说法 | 出处 |
|------|------|
| 金额/积分/有效期以服务端 **`data/pricing.ts`** 为单一真相源 | `docs/05:27`、`docs/15:45` |
| 价格以 **`payment_products` 表优先**、`data/pricing.ts` 为回退 | `boundary-spec:45`、`docs/02:115/133/153`、`docs/01:377`、`docs/16:194`、`provider-abstraction:230` |

**7 处说表优先，2 处说文件是唯一真相源，且说「唯一真相源」的正是支付主文档。**

这不是措辞问题：如果 DB 表才是权威，那么 `docs/05 §5.2 P1-定价-1` 自认的「管理员定价更新逐条执行非事务、无最大金额/货币白名单/积分最小单位/价格积分比例校验、无双人复核」就直接落在**收款金额的权威源**上，应从 P1 升 P0；`P-1.1` 那条 ✅（「杜绝 0 成本攻击」）的防线也只覆盖了客户端，没覆盖后台。

**修法**：先钉死哪个是真相源，再重定级 P1-定价-1，并给定价写入加不变量校验（最大金额、货币白名单、积分/价格比例上下限）+ 事务 + 审计 + 双人复核。

### P2-1 积分有效期在下单时刻冻结

`orders.expired_at` 注释是「积分过期时间」，但它在 `docs/05 §1.3` 第 5 步（**创建 checkout 之前**）就按 `now + valid_months` 算好并随订单 INSERT——有效期从下单时刻而非付款时刻起算，用户在收银台停留、3DS 验证的时间全由用户承担。上界约等于渠道 session 窗口（Stripe/Creem 都是 24h），对最短的 1 个月方案约吃掉 3%。

**修法**（随批次账本改造一起做，成本很低）：批次 `expired_at` 在 `handle_order_payment` 内以 `paid_at + valid_months` 计算；`orders` 只存 `credit_valid_months` 策略，`expired_at` 改为支付时回填的派生列；另加 `checkout_expires_at`（下单时写，定时任务只扫它，对齐渠道 session 生命周期 24h）——顺带定义清楚超时任务的时间基准，`03:173` 目前完全没写。`expired→paid` 恢复设最大迟到窗口（如 7 天），超窗落 `late_paid` 走人工决策，禁止静默充值。

### P2-2 争议/拒付全链路缺失

全 `docs/` 目录 grep `dispute|chargeback|争议|拒付` 只命中 2 处——Creem `§3.5` 一行（处理动作「记录日志」）和 Waffo 能力表一行。**Stripe `§2.3` 的 6 个待处理事件里根本没有** `charge.dispute.created/closed`。

`PaymentEventType` 没有争议类型，`orders.status`（created/paid/expired/refunded/mismatch/deleted）没有 `disputed`/`charged_back`，所以即使收到事件也无处归一化。而 `docs/05 §6` 把 webhook 覆盖缺口归结为「subscription 相关、待 v2」——**争议与订阅无关，v1 一次性付款同样会发生，被漏识别了**。

定 P2 而非 P1 的理由：v1 是 MoR 渠道（Creem 是法律意义上的卖方，Waffo 内置 chargeback 防御），拒付率与商户存活主要由渠道承担；资金在收到事件前已被扣走，增量损失只是「已消费积分不追回 + 账号未冻结可重复作恶」。

**修法**（成本很低）：`PaymentEventType` 加 `dispute_opened / dispute_lost / dispute_won`；`orders` 加 `disputed / charged_back`；`dispute_opened` 立即冻结该用户积分消费（保留余额不删）+ 挂起联盟奖励 + 订单收入移出可确认收入；`dispute_lost` 复用 P0-1 的资产回收 + 债务化 + 风控标记路径；`dispute_won` 解冻。三份渠道文档的事件白名单显式列出争议事件，「已在渠道后台订阅争议事件」写进上线检查项。

## 三、方案里整块缺失的部分

不是某一行写错，是真实收款必备但文档压根没有的章节：

1. **争议/拒付链路** —— 整个资金状态机只有 refund 一条追回路径
2. **账号风险状态机** —— 没有 `restricted` / 欠款 / 冻结消费的概念，所以退款滥用、拒付、债务未清偿三类场景都无处落地（`docs/04:302` 的封禁是通用管理动作，不是资金风控的一环）
3. **退款与滥用的业务条款层** —— 全仓没有「退款政策 / 已消费不退 / 争议举证材料清单」的任何设计。纯技术闭环做不到，行业通行是条款 + 风控 + 举证三件套
4. **迁移的回滚与发布顺序** —— down 脚本、expand-contract 规则、「schema 版本 vs 代码要求版本」校验，一样都没有
5. **AI 成本与错误率的可观测性** —— `docs/16` 全文 grep `ai.` / `成本` / `demo` 零命中；`system.env_or_migration_failed` 是「预留（无发射点）」，迁移失败也没人收到告警
6. **跨实例限流的落地路径** —— `docs/13:209` 自认内存级、多实例不共享、重启清零，`boundary-spec:71/89` 把 fail-open 挂账，但没给设计
7. **并发正确性的验收标准** —— `docs/15-professional-checklist.md` 里一条并发测试都没有。这正是 P0-2 能被标成 ✅ 的原因
8. **对账口径的完整定义** —— P0-对账-1 只写了「渠道成功/退款清单 vs 本地订单/积分/退款」，没有争议、没有「退款成功但积分回收为 0」的专项差异规则，也没有对账失败的处置 SLA
9. **幂等键生命周期** —— TTL、清理任务、请求体指纹、同键异体的返回码，`docs/02` 只有一句「有效期 24 小时」没有落点
